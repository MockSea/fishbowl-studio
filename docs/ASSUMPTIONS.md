# Platform assumptions

Fishbowl Studio was built against a written reference of the MCP, MCP Apps and Cowork plugin formats, not against a running Claude. These are the places where that reference was unverified, or where we had to guess. Each says what we built and what to check first if something misbehaves.

## Packaging and install

**A paid Claude plan with Cowork.** The studio is a Cowork plugin: it needs the Claude desktop app and a paid plan that includes Cowork. Plugins, scheduled tasks and Claude in Chrome are all used. Which plans include Cowork changes over time; we didn't check a plan page.

1. **Plugin at the repository root, marketplace pointing at `./`.** The reference shows plugins in a `plugins/<name>/` folder. We keep one plugin at the root with `"source": "./"` in `.claude-plugin/marketplace.json`, next to `plugin.json`. *If "Add marketplace" fails:* move the plugin into `plugins/studio/` and point `source` there.
2. **The MCP server is declared inline in `plugin.json` (`mcpServers`), not in a root `.mcp.json`.** Both forms are documented for Claude Code plugins; the inline form was used because of how this repository was built. *If the server doesn't start:* add a root `.mcp.json` with the same `mcpServers` block and remove it from `plugin.json` (keep one, not both).
3. **Node.js: a plugin's `"command": "node"` uses the computer's own Node, not the one inside Claude.** Checked on disk against Claude desktop 3.1623.3 (macOS), without running it. The app does ship a Node runtime (Electron's, Node 24.22), and runs MCP servers on it **for installed desktop extensions** (`.mcpb`/`.dxt` with `server.type: "node"`, setting `isUsingBuiltInNodeForMcp`, on by default). The lookup that chooses the built-in Node starts from the installed-extensions list; a server that isn't an installed extension (a plugin's `mcpServers` entry) falls through to running `node` from the app's PATH. So today they need Node.js 20+ installed, and GUI apps on macOS often miss Homebrew and nvm paths. What we did: the server's entry point checks the version before loading anything and, on an old Node, answers every call with one sentence ("needs a newer Node.js … download the LTS installer from nodejs.org, run it, then quit and reopen Claude"); with no Node at all the server can't run, so `/studio:setup` and the skills tell Claude to say exactly that one fix when the `studio_*` tools are missing. *Unverified:* whether Cowork runs plugin servers inside its sandbox VM (which may have its own Node) rather than on the Mac. *To remove the install step:* ship the server as a `.mcpb` bundle as well (manifest `server.type: "node"`, entry `server/index.js`), which uses the built-in Node; the skills and commands would still come from the plugin.
4. **`${CLAUDE_PLUGIN_ROOT}` is substituted in `args`.** Documented for Desktop org plugins. We do **not** use `${CLAUDE_PLUGIN_DATA}` (unverified in Cowork): the data folder defaults to `~/Documents/Fishbowl Studio`, overridable with `STUDIO_HOME`.
5. **The plugin name `studio` gives commands like `/studio:setup`.** Commands are namespaced by plugin name. The name is generic; if it collides with another plugin, rename it (and update the docs) before the first public release, since renaming later breaks installs.
6. **Upload plugin accepts a zip whose root contains `.claude-plugin/`.** `npm run pack` writes `dist/fishbowl-studio.zip` that way. If upload wants a top-level folder, zip the folder instead.
7. **Skill frontmatter uses only `name` and `description`**, and skill folder names match `name`, per the reference's warning that other keys are hard errors outside Claude Code.
8. **Tool names inside Cowork** may carry a prefix (Claude Code uses `mcp__plugin_<plugin>_<server>__<tool>`). Skills refer to tools by their bare `studio_*` names and say a prefix may appear.

## Protocol

9. **Legacy MCP handshake.** The server speaks the `2025-11-25` `initialize` handshake (it echoes 2025-06-18, 2025-03-26 and 2024-11-05 too) and answers `server/discover` and other unknown methods with `-32601`, so a dual-era host falls back to `initialize`. Unverified which era Cowork uses for stdio servers.
10. **`ping`** returns `{}`; **`resources/templates/list`** returns an empty list. Both standard, neither confirmed against Claude.
11. **Non-UI tools return text only**, no `structuredContent`, because some hosts pass the structured JSON to the model instead of the text. The board tools (`studio_board`, `studio_view`, `studio_act`, `studio_proposals`, `studio_proposal_decide`, `studio_wizard`) return both, and their structured content is readable by a model, so item text in it is cleaned to one line but is not fenced. `studio_posting` puts the queued posts in its text as a JSON block, so each post's text reaches Claude exactly.
12. **The host enforces `visibility: ["app"]`.** These are app-only, so only their clicks on the board reach them:
    - `studio_proposal_decide`: accept or reject a proposal, including the setup wizard's drafts and adding a suggested source;
    - `studio_source_add`: adding anything the studio reads;
    - `studio_account_set`: connecting an account;
    - `studio_account_posting`: turning "Post for me" on or off for an account (turning it on also needs `confirmed: true`, which the board sends only from the warning's **Turn it on** button);
    - `studio_post_schedule`: approving a draft to be posted (the board's Approve, Save & approve, Post it for me and Try the next slot), and clearing a missed or failed post.

    The server can't tell who called a tool; if a host lists app-only tools to the model anyway, the model could accept its own proposals, add a source, or turn posting on and approve its own drafts for posting. This is the one assumption both guarantees rest on: "nothing new is read without their tap" and "nothing is posted without their tap". Approving in chat (`studio_act`) never schedules a post, and no other tool writes the accounts file. Unverified for Cowork.

## The board (MCP App)

13. **Bridge shape.** The board uses raw JSON-RPC over `window.parent.postMessage` with the SDK's `ui/initialize` shape (`appInfo`, `appCapabilities`, `protocolVersion: "2026-01-26"`). Rebuilt from field names in the ext-apps source, not observed traffic. Unverified whether mobile WebViews need a different transport.
14. **`ui/notifications/tool-input` is never relied on** (reported missing in Cowork). The board waits 0.8 s for `tool-result`, then loads its own data with `studio_view`.
15. **Resource metadata**: `prefersBorder: false`, `csp.resourceDomains: ["https://assets.claude.ai"]` (for host fonts), `permissions.clipboardWrite: {}`, and no `domain` (stdio servers must not set one). Unverified that `clipboardWrite` is honoured. The Copy button falls back to `document.execCommand('copy')`, and if both fail it asks them to select and copy by hand.
16. **`ui/message`** (the "Ask Claude now" buttons, Add account, the setup wizard's **Draft it for me** and **Set it up for me**) is assumed to post a user message into the chat, which Claude then acts on in the same session. If the host refuses, the board shows the exact words to type instead. The wizard then waits for Claude by reloading its data every 4 seconds for up to 5 minutes, with a **Check now** button after that; it never assumes the message arrived.
17. **`ui/open-link`** opens the story; local servers always get a confirmation prompt. If refused, the board shows the URL.
18. **Every tool call mounts a new board.** Older boards listen on a `BroadcastChannel` and show "a newer board is open" when a newer one announces itself. If `BroadcastChannel` isn't available in the sandbox, old boards stay live; fingerprints still stop them overwriting newer text.
19. **No board in some surfaces.** MCP App panels reportedly don't mount in mobile Cowork or in cloud-run sessions. Reviewing works in chat (`studio_board` returns a text list) and so does the setup wizard (`studio_wizard`), but their board-only decisions (keeping proposals, adding sources, turning posting on, approving to post) wait until they open the board on the desktop.
20. **HTML size.** The assembled board is about 150 KB with both skins; no size limit was found in the reference.

## Scheduling and runtime

21. **Cowork scheduled tasks, created by Claude.** Cowork gives Claude `list_scheduled_tasks`, `create_scheduled_task` (cron expression or one-time) and `update_scheduled_task` (seen in the app bundle, not exercised), and creating one asks them to approve it on a card. The board's **Set it up for me** sends Claude the task names, cron expressions (e.g. `0 7 * * 1-5` for weekdays at 7:00), prompts and folder, and asks it to update rather than duplicate. If the tool isn't there, the Schedule page keeps the click-by-click steps ("Scheduled → New task …") with copy buttons; those labels may differ. A plugin still can't create a schedule by itself.
22. **The scheduled task can use the plugin's tools and skills.** Assumed, since the task runs a normal Cowork session with the folder attached.
23. **Releases happen lazily.** Batches release whenever any studio tool is called after a release hour (opening the board, the status check, the scheduled run). If nothing touches the studio all afternoon, the 12:00 and 16:00 batches release together the next time they look. This matches the original's "missed batches run as one".
24. **Local time.** Release hours and posting slots use the computer's local time zone.
25. **One writer at a time.** If the scheduled run and an open board act at the same moment, a lock in `state/.lock` serialises them (stale locks older than 30 s are broken).
26. **Network.** The server's own network calls are `studio_fetch`, `studio_wander`, `studio_draft_link`, the test-fetch when they add a website or subreddit, and reading the page they link in the setup wizard (all through the same path: built-in `fetch`, 15 s timeout, 3 MB cap, HTTPS only, public hosts). LinkedIn pages linked in the wizard aren't fetched (they need a login). Claude's browser and web-search reads, and posting, are Claude's, not the server's. Nothing else leaves the machine.

## Reading social sites

27. **Subreddit feeds.** Every public subreddit serves `https://www.reddit.com/r/<name>/.rss` (Atom). Reddit rate-limits and sometimes blocks unfamiliar user agents (HTTP 429 or 403); a blocked subreddit shows as "Not responding" like any dead feed. Unverified how often that happens with the studio's user agent.
28. **X and LinkedIn logged out.** Claude reads the public page with its browser tool (Claude in Chrome). Since 2023 X shows logged-out visitors little or nothing of an account's timeline, and LinkedIn often redirects company pages to a sign-in wall. Expect many `login_wall` results; the skill then reports it and the board says "Asks to log in". The web-search fallback finds posts only when other sites quote them. Unverified what a logged-out Claude in Chrome sees today.
29. **X trending topics** (`x.com/explore/tabs/trending`) may need a login too; same handling.
30. **Claude in Chrome in a scheduled task.** Unverified whether a Cowork scheduled run has the browser tool, or whether the extension needs Chrome open. If it doesn't, the skill reports `no_browser`, falls back to web search, and the board says so.
31. **Claude's web search in Cowork** is assumed available to the daily run for saved searches. If it isn't, the skill reports `failed` for those targets and the run carries on.

## Posting for them

32. **Posting goes through their own signed-in Chrome.** The `post` skill opens each platform's composer with Claude in Chrome, in the browser profile they signed in to, and posts the approved text. Where the platform documents a share address that fills the composer (`accounts/<type>.json` `prefill`: X `x.com/intent/tweet?text=`, Bluesky `bsky.app/intent/compose?text=`, Threads `www.threads.com/intent/post?text=`), the server builds that address from the approved text, so the words in the composer come from the server, not from Claude typing them; Claude only presses Post. LinkedIn has no documented one, so there Claude opens `compose` (`linkedin.com/feed/?shareActive=true`) and types the text, and the `check` step compares what Claude says it will type, not what the page holds. Either way, what was actually published is what Claude reports back: the server can't read the platform, so a post that went out different from the approved text would only show on the platform itself. Unverified: that a scheduled run gets their signed-in Chrome (see 30), that those addresses open a composer, and that the skill can find the Post button reliably on each site. Any of these failing shows on their board as a failed post with its reason (`no_browser`, `not_signed_in`, `composer_changed`, `site_refused`); nothing is retried.
33. **Automated posting breaks platform rules.** X's rules and LinkedIn's User Agreement forbid automated posting outside their APIs, and Meta's terms for Threads restrict automated access; any of them can restrict the account. Bluesky is more open to automation but still acts on spam. This is why "Post for me" is off by default, per account, and turned on only on the board after a plain warning (`post_warning` in each account file), with when it was turned on and off kept. The official-API route (or a scheduler service) remains the safer one; it would plug in at the same `handOff()` gate.
34. **The computer has to be awake.** Posting happens in a Cowork scheduled task ("Fishbowl Studio posting", five minutes after each release hour of every brand with posting on). If the computer is asleep or Claude is closed, nothing runs: a slot more than 60 minutes old is marked **missed** with that reason, and a post Claude took but never reported on is marked **failed** after 30 minutes with "check before you try again: it may have gone out". Neither is posted late or retried by itself; they tap **Try the next slot** or copy it.
35. **The text check is exact.** At approval the server keeps a SHA-256 of the approved text (line endings normalised). Before typing, the skill sends the exact text it is about to post; the server compares it with that hash and with the draft's current text, and says go only if all three match. If a site rewrites the text on the way in (say, shortening a link), the posted text can differ from the approved one; drafts carry no links by default.
